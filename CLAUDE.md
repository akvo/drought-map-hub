# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Drought-map Hub: a platform for validating, publishing, and exploring Combined Drought Indicator (CDI) maps. Three moving parts that only make sense together:

- **`app/`** — the web application: Django REST backend + Next.js frontend + Postgres + Rundeck + a DjangoQ worker.
- **`cdi/`** — the CDI computation pipeline (NDMC scientific scripts + shell orchestration) that produces GeoTIFF/GeoJSON drought maps.
- **`geonode/`** — the spatial data infrastructure (external, run via its own compose). Stores raster + aggregated vector outputs; the backend talks to it only over its HTTP API.

Data flow: Rundeck runs the `cdi/` pipeline monthly → outputs upload to GeoNode (category `cdi-raster-map`) → pipeline hits a backend endpoint to create a `PublicationProcess` → reviewers/admins validate in the web app → published maps served to the public frontend.

## Running & common commands

Everything runs in Docker. The top-level `run.sh` is the entry point:

```bash
./run.sh mode=dev service=all     # start db, backend, frontend, worker, rundeck, geonode, cdi
./run.sh mode=dev service=app     # just the web app stack
./run.sh down                     # stop everything
./run.sh ... --dry-run            # print the compose commands without running
./configure.sh                    # first-time setup for a NEW client instance (writes .env files, seeds users, creates Rundeck project)
./post-installation.sh            # one-off GeoServer config (admin password + XML entities) after geonode is up
```

Dev uses direct port access; **prod mode adds the Traefik reverse proxy** (`traefik/`). Backend ~:8000, frontend :3000, Postgres :5433, Rundeck :4440.

### Tests

Tests run inside containers via `app/docker-compose.test.yml` — this is what CI (`ci/test.sh`) does and the reliable way to reproduce failures:

```bash
# Backend: runs migrate, then coverage over `manage.py test` (shuffled, --parallel 4), then generates db.dbml
docker compose -f app/docker-compose.test.yml run -T backend ./test.sh

# Frontend: yarn lint + prettier --check + jest
docker compose -f app/docker-compose.test.yml run --rm --no-deps frontend sh test.sh
```

Single test (run inside the respective container, cwd `/app`):

```bash
./manage.py test api.v1.v1_publication.tests.<module>.<TestCase>.<test_method>   # backend
yarn test <path-or-pattern>      # frontend (jest); yarn test:watch to iterate
```

### Lint / format (match these; CI enforces them)

- Backend: `flake8` (config in `app/backend/.flake8`), `black`, `isort`.
- Frontend: `yarn lint` (eslint-config-next), `yarn prettier`.

## Backend architecture (`app/backend/`)

- Django 4.2 + DRF, Python 3.9. Settings: `drought_map_hub/settings.py`. API docs at `/api/docs/` (drf-spectacular).
- **Custom user model `v1_users.SystemUser`** — never reference Django's default User. Auth is JWT (`djangorestframework-simplejwt`). Roles/abilities are seeded and enforced (CASL mirror on the frontend).
- APIs are grouped by domain under `api/v1/` — each is a Django app with its own `models.py`, `serializers.py`, `views.py`, `urls.py`, `tests/`, and `management/commands/`:
  - `v1_init` — bootstrap/config (incl. `generate_config` → frontend config, see below)
  - `v1_users` — accounts, roles, invitations
  - `v1_publication` — the core review/validation/publish workflow (largest: `views.py` ~29KB)
  - `v1_jobs` — DjangoQ-backed background tasks (automation monitoring, map downloads)
  - `v1_rundeck` — Rundeck integration (trigger/track CDI jobs)
  - `v1_setup` — first-run instance setup
- **The DB schema name comes from `DB_SCHEMA` env var and is `dmh_app`** (recently renamed from `drought_map_hub` — code/migrations reference `dmh_app`, the Python package stays `drought_map_hub`).
- `worker` service runs DjangoQ (`run_worker.sh`) against the same codebase for async jobs.
- Geospatial processing uses `geopandas`, `rasterio`, `rasterstats`, `topojson`.

### Frontend config is generated by the backend

`generate_config` (run in `seeder.sh`) reads `source/country.topojson` and writes `source/config/config.min.js` embedding the country boundaries as TopoJSON. The Next.js app consumes that generated config — **changing country/boundaries means regenerating this, not editing frontend code**. `country.topojson` is client-specific per instance.

## Frontend architecture (`app/frontend/`)

- Next.js 14 **App Router** (`src/app/`), React 18. Routes map to areas: `publications/`, `reviews/`, `browse/`, `compare/`, `setup/`, `settings/`, `(auth)/`, `iframe/` (embeddable map).
- Maps: Leaflet + react-leaflet (+ `leaflet.pattern`, `@turf/turf`, `topojson-client`). UI: Ant Design + Tailwind + Sass.
- Auth/session handled in `src/middleware.js`; permissions via `@casl/ability` (mirrors backend roles). Rich text via TinyMCE.

## CDI pipeline (`cdi/`)

- `src/cdi-scripts/` — NDMC scientific scripts, ordered by filename (`STEP_0000` runs all; `STEP_01xx` ingest LST/NDVI/CHIRPS/soil-moisture, `STEP_02xx` percentile-rank, `STEP_03xx` weighted-sum CDI + export rasters). Settings in `cdi_*_settings.conf`.
- `src/background-jobs/` — shell orchestration (`job_00_login` → `job_01_check-dataset` → `job_02_extract` → `job_03_run_cdi` → `job_04_upload_to_geonode`). `change-cdi-bounds.sh` / `change-cdi-weight.sh` reconfigure the pipeline per instance. Some datasets need **NASA Earthdata credentials** (in `cdi/.env`).
- Rundeck triggers these on the remote CDI VM; the VM/node and auth are configured manually in Rundeck (see README §5).

## Conventions that aren't obvious

- Backend management commands are the interface for seeding and config — browse `api/v1/*/management/commands/` before writing one-off scripts (`generate_administrations_seeder`, `generate_roles_n_abilities_seeder`, `fake_*_seeder`, `generate_config`, `check_overdue_reviews`).
- `check_overdue_reviews` is meant to run as a daily cron (emails reviewers past due); it's not triggered by app traffic.
- Env files are per-service and gitignored: `app/.env`, `app/rundeck.env`, `cdi/.env`, `geonode/.env` (templates: `env.example`, `rundeck.env.template`). `configure.sh` populates them.
- CI only runs the backend and/or frontend suite when files under those paths changed (and always on `main` pushes).
